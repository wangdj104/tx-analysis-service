## 本轮五项修复范围

以下是实施范围，最终结果以本文件末尾的验证记录为准。

1. **[告警规则更新的患者归属](../src/main/java/org/familyhealthcare/service/impl/AlertServiceImpl.java)**：更新前读取原规则、核对原患者的写权限，阻止换一个患者编号来修改别人的规则；保留原记录所有者，不改告警阈值的含义。
2. **[自动分析的当前访问权](../src/main/java/org/familyhealthcare/service/HealthAnalysisAutomationService.java)**：任务属于创建人，并不表示创建人永远能看患者数据。列表按当前完整档案读取权限过滤；引用的分析还必须与任务属于同一个患者、同一个作者。审核在任何字段修改之前检查完整档案写权限。
3. **[后台通知的实际接收人](../src/main/java/org/familyhealthcare/task/FamilyCareTask.java)**：发送前重新核对原定接收人的当前权限、账号及患者状态。旧成员关系、已撤销授权、失效医生角色不能单独恢复接收权；不会因此扩大群发范围。
4. **[普通 CSV 的公式防护](../src/main/java/org/familyhealthcare/service/impl/DataExportServiceImpl.java)**：把危险开头的文本作为文字导出，防止表格软件把备注当公式执行；真正的数字保持数字，原始业务字段不被改写。

### 后续处理顺序

以下是工程处理优先级，不是已经完成漏洞利用验证的严重性评级。

1. **先处理可能丢数据或让审核/临床记录与实际保存内容不一致的链路**：导入事务、附件失败回退、审核内容版本、透析局部更新和 null 字段持久化。最小下一轮建议只覆盖“附件写入失败”和“导入中途失败”两个场景，先用真实 Spring 事务与 mapper 证明最终数据库内容，再单独修复；临床派生字段另开有数据样例的回归，不夹带公式调整。
2. **对外启用前确认访问与失败边界**：Webhook 出站范围、AI 菜单路径、改密后的令牌策略，以及 AI 失败文本进入分析草稿。先明确部署和调用约定，再做针对性的接口/持久化测试。
3. **随后处理可用性和防御加固**：自动任务认领/恢复、导入来源去重和传统下载的禁缓存头。自动任务在多实例或频繁重试的部署中应提高优先级。

上述条目需要单独验证和修复；本轮通过的测试不能替代这些缺口的验收。

旧用药/家庭提醒仍有“先发送、后写成功标记”的窗口。这次补的是发送资格检查，不承诺严格只发送一次，也不能把授权撤销与外部渠道收件变成一个原子操作。

## SQL 运维注意

- 新库不是只跑 `init.sql`；按目录完成依赖链
- 旧库先确认现有结构，再选择缺失升级。存在检查不等于修正所有历史类型、索引或半完成状态
- 权限清理脚本会删除旧角色和关联，不是普通“只加表”升级
- 专病角色脚本目前会在每次 MySQL/MariaDB 应用启动时运行，手动执行过不会关闭这一行为
- MySQL DDL 会隐式提交，不能把事务包裹当成整份脚本可回滚
- 历史 `RunSqlMigration.java` 仅备份六张表；家庭档案导出也不是全库备份
- 完整备份还要包含附件/对象存储、应用版本和配置，并在隔离环境演练恢复
- 本轮真实 MySQL 验证只使用已有 CI 的临时合成数据库，不证明兼容每一种历史结构
