# 照护计划协作闭环：第一里程碑设计规格

- 日期：2026-10-03
- 状态：待用户审阅；本文不是实施计划，也不代表功能已经实现
- 代码核对基线：`b2767a22f268a9cfae54b61c71c2c4e73f7cdb75`
- 范围：个人、家庭与医生/护理团队围绕同一个患者计划协作

## 1. 目标、依据与成功定义

用户确认平台最终服务个人、家庭以及管理患者的医生/护理团队，并认可先打通计划到执行反馈的方向。完成标准是可验证的产品闭环，不是固定工作小时数、页面数量或测试数量。本文将这一方向收敛为一个可交付子系统；技术细节仍需通过本文审阅确认。

第一里程碑让医生发布明确行动，个人看到下一步，授权家属协助记录，护理人员跟进困难，医生复核执行反馈。系统记录谁、在何时、依据哪个版本进行了什么操作。患者自报执行与医生复核必须清楚分开；复核表示记录已处理，不证明治疗有效。

不根据自由文本自动拆医嘱、改变药量、给出诊断或生成新的临床阈值。所有示例与测试使用合成数据，不向真实患者发送测试通知。

### 当前已有能力

- 医生计划 `doctor_care_plan` 有列表和新增，尚无患者端发布、执行回执与关闭闭环：`DoctorWorkspaceService`、`DoctorWorkspaceController`、`frontend/src/views/DoctorWorkspace.vue`
- 家庭 `care_item` 已有预约、交接、问题、症状、活动日志；用药已有独立提醒、打卡、库存和升级通知：`FamilyCareService`、`FamilyCareTask`、`CareCenter.vue`
- 正式预约已有自动复诊、冲突处理；治疗计划和康复打卡也已存在：`CareJourneyService`、`CareJourneyTask`
- 时间线、就诊摘要和报告已有基础：`HealthTimelineService`、`FamilyHealthController`、`HealthReportServiceImpl`
- 模块授权、READ/WRITE/PROXY、撤销/过期控制与通知日志已有基础：`DataScopeHelper`、`NotificationAudienceService`
- `doctor_patient_assignment.care_team_role` 只是医生分配标签；现有分配入口验证 doctor 角色，不能视作已支持独立护理角色

### 方案选择

采用“现有医生计划 + 独立执行生命周期 + 现有页面投影”。不把临床计划伪装成允许自由编辑删除的 HANDOVER；也不重写用药、预约、康复三套已有流程。新增跨角色契约、状态机和数据库关系，因此属于架构级变更。

## 2. 第一里程碑边界

### 包含

1. 医生计划草稿、明确发布、发布版本、取消与医生关闭
2. 每个版本 1–50 个一次性行动项：说明、期限、责任人、可选既有记录引用
3. 患者本人记录、授权家属/护理人员协助记录、困难反馈及医生复核
4. 护理角色、患者分配及最小权限，医护跟进队列
5. 今日照护、计划详情、医生工作台、护理队列、受权限控制的时间线集成
6. 新流程的持久通知任务、渠道结果、受限重试和发送前权限复核
7. 增量升级、历史记录兼容、双语界面与合成端到端验收

### 不包含

- 通用周期任务引擎、新用药执行引擎、自动预约、自动临床决策
- 护理人员处方/诊断/临床计划发布权限，自动凭角色获得全病历权限
- 新附件上传、外部设备接入、医疗机构身份资质认证、HIS/药房对接
- 全平台灾备重写、所有既有通知迁移、跨机构租户隔离改造
- 宣称改善血压、依从性、住院率等未经临床验证的效果

## 3. 角色、患者范围与授权

新增模块键 `CARE_PLAN`。任何入口都调用同一个显式授权服务，不依赖 URL 推断、多页面拼装或者前端按钮判断。

| 身份 | 读取 | 执行记录 | 发布/修订/复核/关闭 |
| --- | --- | --- | --- |
| 患者记录所有者 | 本人已发布版本与历史 | 本人记录或按现有监护关系代录 | 不允许 |
| 家属 | 当前有效 CARE_PLAN READ/WRITE/PROXY 授权 | WRITE/PROXY 可协助；READ 不可 | 不允许 |
| 医生 | 当前有效医生患者分配范围，含草稿 | 可记录跟进，不冒充患者自报 | 当前有效分配医生可操作 |
| 护理人员 | nurse 角色有效、护理分配有效，且有患者 CARE_PLAN 授权 | WRITE/PROXY 可协助和记录跟进 | 不允许临床发布、修订、最终复核和关闭 |
| 仅管理员 | 管理分配及配置，不由新功能赋予临床正文访问 | 不允许 | 不允许；临床动作须同时满足医生资格和患者分配 |

### 护理成员的具体规则

- 添加稳定角色码 `nurse`，不把护理人员包装为 doctor 或 family
- 新增护理患者分配关系，管理入口沿用管理员分配治理；须显示分配者、开始时间、结束时间、状态
- 分配只建立团队关系；患者/监护所有者通过既有授权入口授予 CARE_PLAN 范围。管理员建立分配不能代替这一授权
- 护理人员只处理同时满足“有效分配 + 有效模块授权”的患者；未满足时不返回患者正文或任务标题
- 医生分配沿用原有规则；本文不改变已有医生全档案权限模型
- 第一里程碑护理队列仅管理本闭环，不自动授予处方、心理、问诊或其他既有模块权限

### 读取和操作必须验证

- 账户启用、角色有效、患者存在且可用、分配/授权有效且未到期
- 计划、行动项、回执、引用记录属于同一患者；以数据库归属为准，忽略伪造 patientId
- 有专门授权记录时，不回退旧的宽泛 family membership 绕过撤销或模块限制
- 分配给某人的行动项不构成访问授权；选负责人时校验其当前权限
- 家属失去权限后，患者仍能处理行动；界面显示“协助人已不可用”，不给失权用户发通知，不自动扩大别人权限
- 医生失去分配、护理失去角色/分配或授权后立即停止访问；其他有效分配医生可接续复核
- 查看旧快照也要求当前权限；历史作者身份不是永久访问权
- 引用的测量或病历要求其原模块当前读取权限。只有 CARE_PLAN 权限时显示“存在受限关联记录”，不返回标题、数值、下载地址或内容

## 4. 计划发布、版本与旧数据

### 计划聚合

现有 `doctor_care_plan` 保留身份及原字段，新子系统通过 `workflow_version=1` 区分。新生命周期字段独立于旧 status，避免改变旧接口含义。

- `DRAFT`：仅有效分配医生可查看/编辑，不能出现在患者、家属、护理队列和通知
- `ACTIVE`：至少一个已发布版本；患者可看当前发布内容
- `COMPLETED`：医生明确关闭且当时所有当前行动项已复核确认
- `CANCELLED`：医生明确取消并记录原因

医生新增后首先保存草稿。发布需标题、说明、1–50 个行动项、截止时间和负责人均有效。发布动作在一个事务中固定版本快照、创建行动项、审计事件与通知任务。既有管理员绕过逻辑不能成为新临床动作的授权捷径。

### 修订

- 已发布临床说明不可原地覆盖；医生创建下一版本草稿，发布前旧版本继续有效
- 发布修订时必须展示差异以及未完成/待复核项处理结果，要求医生明确确认
- 新版本产生一套新的行动项；旧版本未终结的项统一标记 SUPERSEDED，既有回执继续归原版本，不自动算到新版本
- 已确认项保持历史 CONFIRMED，不自动复制为新版本已完成
- 不支持“悄悄修改截止时间”；期限变更走新版本。护理可记录延期请求/困难，不能自行更改临床安排
- 第一期完成或取消的计划不能重新打开；需要继续照护时创建明确的新计划，可关联旧计划 ID

### 旧 ACTIVE 计划

旧计划加上 `workflow_version=0`，其原字段、状态、列表和可见范围保持不变。它们仍是医护内部旧记录，不自动发布、不自动生成行动项、不自动触发通知。

医生可用“复制为协作计划”创建新的草稿并关联 legacy_source_id；旧记录保留。转换与发布是两个明确动作。旧版 POST 接口继续创建 legacy 记录，不因升级偷偷变成已发布计划。旧列表兼容返回，但标记“历史内部计划”，不将它计入新闭环统计。

## 5. 行动项、回执及跟进生命周期

### 行动项状态

- OPEN：待执行
- NEEDS_HELP：个人或协助人说明遇到困难，进入医护跟进队列
- SUBMITTED：已提交执行回执，等待医生复核
- CONFIRMED：医生已复核记录；界面不表述为治疗成功
- SUPERSEDED：所属版本被新版本替代
- CANCELLED：所属计划已取消

逾期为派生标记：当前时间晚于截止时间且状态为 OPEN/NEEDS_HELP。已在期限前提交但仍待医生处理的项目，不算患者逾期。另单独展示提交至今的待复核时长。

### 允许的动作

- OPEN → NEEDS_HELP：说明困难，非空原因；可追加新的跟进备注
- OPEN/NEEDS_HELP → SUBMITTED：提交已执行说明、实际执行时间及可选引用
- SUBMITTED → CONFIRMED：医生确认已复核；记录复核人、时间和可选意见
- SUBMITTED → OPEN：医生要求补充，必填说明；旧回执不可删除
- OPEN/NEEDS_HELP/SUBMITTED → SUPERSEDED 或 CANCELLED：仅由计划级修订/取消事务执行
- CONFIRMED 及其他终态不能通过通用 update 接口改写；纠错使用追加记录，不能抹除原证据

医生复核的是任务反馈，不验证疾病改善。若发现原临床指示需要变更，必须使用计划修订，不通过复核意见悄悄替换医嘱。

### 自报与代录

- 操作者由认证会话确定，客户端不能指定 actor_id 或伪造角色
- 患者记录所有者可“本人记录”；如果该账号管理的是其他家庭成员，必须显示“为该成员记录”，不得将账户身份当成患者本人身份的证明
- 家属和护理提交固定标记 ASSISTED，记录操作者关系与角色快照，不允许勾选成患者自报
- 记录 `occurred_at` 与服务端 `recorded_at`；允许过去时间，拒绝未来时间；过去执行时间不被当成及时提交
- 首期单条回执为 1–2000 字，困难/退回说明为 1–1000 字；客户端提示与服务端校验一致
- 不支持新文件上传；每回执最多 5 个既有测量/医疗记录引用，保存时和读取时分别校验归属与权限

护理人员可以记录“已联系、等待补充、已提醒医生”等管理跟进事件；不会把 SUBMITTED 改为 CONFIRMED，也不能关闭计划。其代录提交的回执仍由医生复核。

## 6. 数据边界、事务和并发

### 建议的持久模型

| 对象 | 职责与关键约束 |
| --- | --- |
| doctor_care_plan 增量元数据 | workflow_version、lifecycle、current_revision_id、legacy_source_id、lock_version、关闭/取消时间 |
| care_plan_revision | plan_id + revision_no 唯一；草稿/发布时间；标题与说明快照；发布人；发布后正文不可变 |
| care_plan_action | revision_id + ordinal 唯一；patient_id；责任人；说明/期限快照；状态及 lock_version |
| care_plan_event | 只追加的发布、困难、提交、跟进、退回、确认、修订、取消/关闭事件；actor 与时间快照；关联 action/revision |
| care_plan_evidence | 回执事件与原记录类型/ID 的引用；不复制受限原始内容 |
| care_nurse_assignment | patient_id + nurse_user_id 唯一；状态、到期、分配人；不隐式创建 patient grant |
| care_plan_notification | 业务事件、收件人、渠道、尝试和状态；唯一键阻止重复入队 |
| care_plan_command | 操作者 + command_key 唯一，保存请求摘要和原结果；防重放重复产生实体 |

表间外键禁止级联删除历史；涉及旧表类型的约束须在实施前核对 MySQL 列类型兼容。状态采用稳定字符串并由服务端白名单及状态机验证。修改对象使用带预期版本的条件更新，不以最后写入覆盖别人结果。

### 幂等与竞争规则

- 发布、修订、回执、复核、取消/关闭必须带 command_key 与 expected_version
- 同一操作者同 key、同载荷返回原结果；同 key 不同载荷返回 409
- 即使重放成功结果，也先重新检查当前读取/操作授权，不把原响应泄露给已失权用户
- 同时提交或确认只允许一个成功；另一方得到 409 和刷新提示，不丢弃本地输入
- 所有变更按计划聚合串行锁定或等价原子事务执行；取消/修订与回执竞争时，不允许回执落到已经终结的行动项
- 发布与事件/通知入队同事务，事务失败不得有孤立任务或通知
- 外部 webhook 不能保证恰好一次。保存请求标识和结果；连接中断且结果不明时标记 UNKNOWN，不自动重发，避免盲目重复通知

### 时间

新流程使用带偏移的 ISO 8601 输入和 UTC 持久化，显示浏览器本地时间并注明时区。截止时间必须由医生明确确认，不把单独日期隐式解释成服务器午夜。新表不混用旧计划的 target_date 进行提醒计算；旧日期只在转换草稿时提示补充时间。

## 7. 通知和可见性

新计划的执行入口在应用内持久可见，不依赖某个 webhook 配置成功。

- 事件：发布/修订、困难、提交待复核、退回、确认、取消/关闭
- 患者与当前有效协助负责人接收与其相关事件；医生/护理队列根据工作范围展示，不向所有亲属广播
- 首期不增加按分钟催促的重复提醒；逾期在应用内排序展示，并生成一次到期通知
- 外部消息只包含通用通知文字及受登录保护的相对页面定位，不含患者姓名、诊断、任务正文或指标
- 入队、领取发送前和人工重试时重新检查账户、患者、模块授权/分配；失权标记 SUPPRESSED
- 状态明确区分 QUEUED、DELIVERED、NO_CHANNEL、FAILED、UNKNOWN、SUPPRESSED，不将所有失败写成无渠道，也不将已投递表述为已读
- 对明确可重试失败最多总计 3 次，首次后约 1 分钟和 5 分钟重试；每次重新校验权限。UNKNOWN 不自动重试，人工操作需提示可能重复
- 每业务事件/收件人/渠道仅一个持久发送任务，使用数据库领取锁防止多实例并发发送；旧通知机制不在本里程碑整体迁移
- 新事件需要本地化和 CARE_PLAN 模块映射，不能依赖 NotificationAudienceService 对未知事件的宽泛处理

## 8. 页面、时间线与历史

### 医生工作台

保留既有计划入口；新增草稿/当前协作计划/历史内部计划区分。计划编辑器明确展示发布范围、行动项、负责人和期限。待复核、困难、逾期分别列队，点击直达相应计划/回执。医生明确执行发布、修订、取消、确认和关闭。

### 个人和家庭的今日照护

在现有 CareCenter 增加“医生计划事项”独立分组，与用药打卡、预约、HANDOVER 区分来源。卡片展示发布医生、版本、责任人、期限与当前状态；读取权限不足时隐藏正文，不通过 aggregated `/care/context` 扩大原有全档案授权。

新模块使用独立受 CARE_PLAN 权限控制的列表接口，即使用户只有模块授权、无法打开旧的全档案聚合接口，也能使用计划事项。返回仅包含计划最小上下文，不捎带药物、病历、家属列表等无关数据。

### 护理队列

为 nurse 提供新的受限队列入口，按困难、待跟进、待医生复核展示其授权患者。不能因菜单可见而访问整个 DoctorWorkspace 或全部 CareJourney 运营数据。失去一个授权患者后立即从队列移除。

### 时间线与记录快照

第一期新增计划发布、修订、执行提交、医生复核、取消/关闭的 CARE_PLAN 投影。事件 ID 与 source_type 组合稳定，不因刷新重复创建 health_event。

优先在读取时由独立 CARE_PLAN 事件投影器加入时间线，避免将完整临床快照复制进权限较宽的通用 health_event。投影器显式检查 CARE_PLAN 权限，通用时间线没有该权限就不返回该类事件。详情再次授权；受限证据不会通过时间线摘要泄露。

历史版本和回执不可被新版本覆盖，但历史可见性取决于当前授权。原作者、代录人、复核人显示事件当时角色；当前离职/停用不篡改历史，也不保留其访问权。

### 交互稳定性与可访问性

EN/CN 同一协议、本地化文案；手机 390px 无整页横向溢出，触控主操作至少 44px，键盘可达且对话框焦点可恢复。加载、空列表、拒绝访问、冲突、失败和只读状态均有明确反馈。

切换患者或退出即清除敏感上下文；旧响应不可覆盖新患者；A→B→A、同患者弹窗重开、重复点击、关闭后晚到写入结果、返回/前进和刷新均有回归覆盖。关闭弹窗不宣称已取消发出的服务端提交。

## 9. API 与服务边界

新增独立 `CarePlanService`（事务与状态机）、`CarePlanAuthorizationService`（角色/患者/模块判定）、`CarePlanQueryService`（最小数据投影）、`CarePlanNotificationWorker`（持久发送）和事件投影器。职责不能继续堆进已有大型 CareJourneyService。

API 使用 `/care-plans` 命名空间，包含：创建草稿、读取授权列表/详情、编辑草稿、发布、创建修订、回执提交、困难/跟进、医生复核、计划取消/关闭。动作使用明确子资源，禁止客户端直接 PATCH 任意 status。护理分配使用管理员受控入口；患者授权仍通过已有 grants 服务，但加入 CARE_PLAN 选项。

响应包含稳定 ID、当前版本、允许动作、实际状态和数据来源。`allowedActions` 仅帮助界面渲染，每个写请求仍由服务端重新验证。未授权 ID 返回统一的不可访问响应，不区分其属于哪个患者；业务版本冲突返回 409。

## 10. 数据升级、兼容与恢复

- 新增单独的幂等增量 SQL；已有安装执行备份后应用升级，不重跑 init.sql

## 11. 验收：以工作流结果为单位

### 核心流程

1. 合成医生创建草稿：患者、家属、护理均看不到；医生发布后正确患者可见且只有一套行动项
2. 合成患者完成一项，家属协助记录另一项；身份、实际执行时间、记录时间和原版本均正确保留
3. 困难反馈进入授权护理/医生队列；护理跟进不修改临床说明；医生退回补充后新回执保留旧回执
4. 医生确认所有当前行动后才可关闭计划；患者自报不直接关闭计划
5. 计划修订使旧待执行/待复核项明确失效；已发生的历史不丢失，也不把历史完成复制为新完成
6. 旧 ACTIVE 记录升级后仍内部可见，复制为草稿也不会自动发布或通知

### 安全与并发

7. 两个患者、两个家庭、两个医生、独立护理角色、管理员和停用账号交叉访问；接口、引用、队列、时间线、通知均拒绝越权
8. READ 家属不能提交；WRITE/PROXY 可协助但不能发布/复核；nurse 无角色/分配/模块授权任一条件就不能访问
9. 撤销/到期在页面打开、写入、历史读取、通知排队与重试各阶段生效；分配负责人不扩大授权
10. 同 key 重放仅一个结果，不同载荷冲突；同时提交、确认、修订、取消不会产生双重状态或孤立事件
11. 未授权引用不泄露数值/标题；历史快照和代录人身份不可被请求篡改

### 通知与运行

12. 用替身验证成功、无渠道、明确失败、结果不明和失权抑制；失败不丢任务，重试上限和领取锁可验证
13. 应用内任务始终可见；外部 DELIVERED 不当作用户已读；未接通生产渠道时不宣称通知已上线可用
14. 服务重启后待发任务恢复，已经确认的动作不重复；断网后客户端重试保留原幂等 key

### UI、迁移与回归

15. 双语桌面与390px流程完成，键盘/焦点、失败重试、只读、患者切换、退出和历史导航覆盖
16. 空数据库完整安装、基线旧库升级、重复升级和含合成新数据的数据库恢复全部通过，EN/CN 结构一致
17. 原预约、用药、家庭 HANDOVER、问诊和既有权限回归通过；新协作不会重定义其既有状态和统计
18. CI、后端打包、双前端构建及必要端到端验证指向最终同一提交；记录通过、失败和未运行项，不以测试总数替代覆盖说明
